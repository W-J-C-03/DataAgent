

### 阶段一：并行召回（三个节点同时出发）

在 LangGraph 中，这三个节点是同时运行的，谁也不等谁。

#### 第一步：召回字段信息 (`recall_column`)

1. **大模型扩词**：输入用户问题，LLM 联想到相关词（如：地区、区域、购买数量、件数）。
2. **向量检索**：拿着这些词去 **Qdrant（向量库）** 里查。
3. **得到结果**：捞出了一堆 `ColumnInfo` 对象，比如：
   * 字段：`region_name`（地区名）
   * 字段：`order_quantity`（订单数量）
   * 字段：`order_amount`（订单金额）
   * 字段：`date_id`（日期）
4. **存进State**：打包存入 `retrieved_column_infos`。

#### 第二步：召回指标信息 (`recall_metric`)

1. **大模型扩词**：输入用户问题，LLM 联想到业务指标词（如：销量、GMV、销售额）。
2. **向量检索**：拿着这些词去 **Qdrant（向量库）** 里查。
3. **得到结果**：捞出了 `MetricInfo` 对象，比如：
   * 指标：`GMV`（成交总额），依赖底层字段 `fact_order.order_amount`。
4. **存进State**：打包存入 `retrieved_metric_infos`。

#### 第三步：召回字段取值 (`recall_value`)

1. **大模型扩词**：输入用户问题，LLM 联想到具体的地名或年份。
2. **全文检索**：拿着扩出来的词，直接去 **Elasticsearch（全文索引库）** 里搜数据库里的真实数据。
3. **得到结果**：捞出了 `ValueInfo` 对象，比如：
   * 值：`"华北"`，它属于 `dim_region.region_name`。
   * 值：`"去年"`，它属于 `dim_date.year`。
4. **存进State**：打包存入 `retrieved_value_infos`。

### 阶段二：合并与组装（核心节点 `merge_retrieved_info`）

现在三个召回员都回来了，手里拿着一堆碎片。合并节点开始**“拼图”**。按照代码顺序，它做了以下 **5 个步骤**：

#### 第 1 步：补全“指标”缺失的底层字段

1. 系统检查：刚才召回了 `GMV` 指标，但字段召回里可能没把 `order_amount` 完整捞回来。
2. 系统操作：遍历所有指标，发现 GMV 依赖 `fact_order.order_amount`。如果发现这个字段没在召回的字段字典里，立刻去 **MySQL（元数据库）** 里查出来，强行塞进字典。

#### 第 2 步：把“具体值”绑定到“字段”上

1. 系统检查：刚才召回了一个值叫 `"华北"`，系统知道它属于 `dim_region.region_name`。
2. 系统操作：在字段字典里找到 `region_name` 字段，把 `"华北"` 这个字符串，强行塞进该字段的 `examples`（数据示例）列表中。
   * *目的：让大模型看到这个字段时，就看到“华北”长什么样，防止它瞎写。*

#### 第 3 步：按“表”重新分组（物理归位）

1. 系统检查：刚才梳理好的字段散落一地（`region_name`, `order_amount`, `date_id` 等）。
2. 系统操作：建立一个大字典 `table_to_columns_map`。以表名（如 `dim_region`、`fact_order`）为 Key，把属于这张表的字段全部按类别塞进 Value 的列表里。

#### 第 4 步：强制补全“主外键”（为了 JOIN）

1. 系统检查：现在有了 `dim_region` 表的字段，也有了 `fact_order` 表的字段。
2. 系统操作：遍历每一张表，去 **MySQL（元数据库）** 里查一下这张表的主键和外键（比如 `region_id`）。
3. 系统操作：如果这个主外键不在刚才分类好的字段列表里，就强行加进去。
   * *目的：大模型写 JOIN 时，必须用主外键，系统提前帮它准备好，防止它漏掉。*

#### 第 5 步：变成标准“卡片”（转为 State 格式）

1. 系统操作：把上面整理好的一堆物理字段，转换成大模型专用格式 `ColumnInfoState`。
2. 系统操作：把表信息（表名、描述、类型）与字段列表打包，生成 `TableInfoState`。
3. 系统操作：把指标信息单独打包，生成 `MetricInfoState`。

### 阶段三：交付给大模型（过滤与 SQL 生成）

经过上面的阶段，最终交给下一个节点（`generate_sql`）的上下文是这样的：

```yaml
# 表结构（含主外键、含示例值）
tables:
  - name: dim_region
    columns:
      - name: region_id (primary_key)
      - name: region_name (examples: ['华北', '华东'])
  - name: fact_order
    columns:
      - name: region_id (foreign_key)
      - name: order_amount
      - name: order_quantity

# 业务指标（计算逻辑）
metrics:
  - name: GMV
    relevant_columns: [fact_order.order_amount]
```

**大模型看到这份完美的结构**，结合用户的问题“统计去年华北地区的销量”，就能极其顺畅地生成 SQL：

```sql
SELECT SUM(order_quantity) 
FROM fact_order 
JOIN dim_region ON fact_order.region_id = dim_region.region_id 
JOIN dim_date ON fact_order.date_id = dim_date.date_id
WHERE dim_region.region_name = '华北' AND dim_date.year = '去年';
```

**这就是从“自然语言”到“精准 SQL”的全过程：三路并发去粗取精，合并节点强力组装兜底，最后大模型自然水到渠成。**
